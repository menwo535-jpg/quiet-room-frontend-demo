02 / Functional QA

Check the effect, not just HTTP 200

A webhook can return the expected response and still create the wrong number of records. A useful test checks both.

14 October 2026 · Independent Workflow Checkbook fixture

Write a contract that can fail

Workflow Checkbook is a synthetic order-intake fixture. A valid event has a stable event ID and a nonempty item list. Each item needs a nonblank SKU and a safe integer quantity from 1 to 10,000. A valid first delivery should create one destination record. A replay of the same event and content should return the original result without a second write.

The suite records the input, response, expected outcome, effect count and an ordered trace. It also includes an intentionally defective implementation. That fixture has incomplete validation, no replay tracking and a success response for downstream failures. It passes only the happy-path scenario; the reference passes all twelve scenario contracts.

Transport success and business acceptance differ

The fake destination can return HTTP 200 with accepted: false. The corrected intake fixture reports a declined business outcome rather than confirming an order. Its chosen contract maps that outcome to HTTP 422. The important point is the explicit business result and the absence of a write, not that every API must use this particular status code.

Try two small observations

Download the fixture module. Save this snippet as an .mjs file at the site root and run it with Node.js. Both requests are local function calls; no real orders, accounts or external services are involved.

import { createFixture, sampleOrder } from './examples/workflow/core.mjs';

const fixture = createFixture('corrected');
const first = await fixture.receive(sampleOrder());
const replay = await fixture.receive(sampleOrder());
console.log(first.status, replay.body.replay, fixture.snapshot().effects.length);
// 200 true 1

const declined = await createFixture('corrected').receive(sampleOrder(), 'declined');
console.log(declined.status, declined.body.outcome);
// 422 'declined'

Make sure the test itself detects defects

One existing test deliberately supplies the correct HTTP response with two effects when the contract expects one. The comparison must fail. This guards against a report that simply accepts a plausible response body without checking the destination state.

Six existing Node tests passed again on 14 October 2026. They exercise the twelve-scenario reference and planted defects, effect-count checking, validation boundaries, snapshot isolation and conflicting event reuse. Place the test file beside the core and run node --test examples/workflow/core.test.mjs.

The fixture is sequential and keeps completed events in memory. It does not establish durable idempotency, concurrency safety, exactly-once external effects or recovery after process restart. Its timeout occurs before a write; an uncertain outcome after a write needs reconciliation and a different test. These are fixture checks, not results from a customer's n8n or voice system.

The useful habit is portable: specify the output and its side effects, then include failures that prove the checker can reject a wrong implementation.
